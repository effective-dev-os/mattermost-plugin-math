## D-002 — Expression evaluation engine: expr-lang/expr
**Date:** 2026-08-25
**Status:** accepted
**Decision:** `/math` will evaluate arithmetic via `github.com/expr-lang/expr`, pinned `>=v1.17.7` (covers both GHSA-93mq-9ffx-83m2/CVE-2025-29786, fixed 1.17.0, and GHSA-cfpf-hrx2-8rv6/CVE-2025-68156/GO-2025-4245, fixed 1.17.7 — do not pin `>=v1.17.0` alone, that leaves the second advisory open). Pin the canonical module path `github.com/expr-lang/expr`, not the legacy `github.com/antonmedv/expr` alias. `^`/`**` mean exponent in expr-lang (not XOR), no gotcha there. `abs` ships as an expr-lang builtin — do not re-register it. `sqrt`, `sin`, `cos`, `log` must be registered manually via `expr.Function`. `sin`/`cos` accept **degrees** (user-facing decision — convert to radians internally before calling `math.Sin`/`math.Cos`), per human confirmation, since chat users expect `sin(90) = 1` not radians.

The plugin must run a text-normalization pass on the raw slash-command string before `expr.Compile`, since no candidate library natively parses human notation. Minimum normalization set (test matrix required before merge, per skeptic critique): `×`/digit-adjacent `x` → `*`; `÷` → `/`; unicode minus (U+2212) and dash variants (U+2013 en dash, U+2014 em dash) → `-`; comma-between-digits → `.` (decimal, not thousands-separator — chat input is assumed single-number, no thousands grouping); implicit multiplication for digit-before-paren (`2(3+4)`), paren-before-digit (`(3+4)2`), paren-before-paren (`(2+3)(4+5)`), and digit-before-function-name (`2sqrt(4)`) → insert `*`; trailing/postfix `%` → rewritten as `/100` on the preceding numeric subexpression (mid-expression `%` behavior must be explicitly decided during implementation — support or reject-with-clear-error, not left ambiguous). Add a hard input-length cap before `expr.Compile` as defense-in-depth alongside the version pin.
**Source:** `swarm-report/research-go-expr-library-2026-08-25.md` (researcher + skeptic + reviewer consilium). Human-approved: library adoption + degrees convention confirmed via AskUserQuestion, 2026-08-25.
**Resolves:** OQ-002.

## D-003 — `/math` implemented: normalization pipeline, percent semantics, log base, package boundary
**Date:** 2026-08-25
**Status:** accepted
**Decision:** `/math <expression>` shipped in `server/command/command.go` (leftover starter-template `hello` command removed entirely — `plugin.json` already scoped this plugin to `/math` only). Normalization + evaluation live in a new package `server/mathexpr` (zero Mattermost imports, pure functions, independently unit-tested), consumed by `server/command` as a service layer. Normalization runs as a fixed-order pipeline: unicode-symbol→ASCII, comma-decimal, percent-rewrite, implicit-multiplication, then a character/identifier allowlist as the final validation step (chosen over `expr.DisableAllBuiltins()` as the single mechanism keeping expr-lang's other ~60 builtins and string/array/pipe/range/comparison syntax unreachable). `expr.Compile` uses `expr.Env(map[string]any{})` (clean compile errors on unknown identifiers) and `expr.AsFloat64()` (uniform float64 result). Dependency pinned at `github.com/expr-lang/expr v1.17.8` (satisfies D-002's `>=v1.17.7` floor; confirmed via OSV/GHSA cross-check that no new CVE was disclosed as of 2026-08-25).

Two decisions not settled by D-002 were resolved during `/pre-feature` by direct analogy to D-002's own degrees precedent, since `AskUserQuestion` was unavailable in this run's toolset and both are documented here for human override:
- **Percent semantics:** every `%` — trailing or mid-expression — is rewritten to `(<preceding operand>/100)`, uniformly, regardless of position. This removes expr-lang's integer-modulo operator from user-facing input entirely (e.g. `10%3` evaluates as `(10/100)*3 = 0.3`, not `10 mod 3 = 1`). Matches the task brief's own "recommended" default and composes cleanly with the implicit-multiplication pass (no special-casing needed).
- **`log()` base:** base-10 (`math.Log10`), not natural log — same "calculator convention over programming-language convention" reasoning D-002 used for `sin`/`cos` degrees (chat users expect `log(100) = 2`).

Other implementation-level decisions: hard input cap of 1024 runes on the raw expression (measured via `utf8.RuneCountInString`, before normalization — matches Mattermost's own `Command.URL` length bound; Mattermost enforces no length cap on slash-command text server-side, so this is not redundant, confirmed against `server/public` v0.1.21 + `api4/command.go`). Division/modulo-by-zero: expr-lang's `/` never errors on zero (`1/0` → `+Inf`, `0/0` → `NaN`, both as *successful* results) — checked explicitly post-`Run` via `math.IsInf`/`math.IsNaN`, mapped to a fixed ephemeral error message. Success responses use `model.CommandResponseTypeInChannel` explicitly (the pre-existing `hello` pattern left `ResponseType` unset, which the Mattermost server treats as ephemeral — not copied). Results formatted via `FormatResult` (epsilon-snap to nearest integer within `1e-9`, `strconv.FormatFloat` with `'g'`/12 precision) so degree-based trig prints clean (`sin(180)` → `"0"`, not `"1.2246467991473515e-16"`).

**Alternatives rejected:**
- `expr.DisableAllBuiltins()` + `expr.EnableBuiltin("abs")` as a second hardening layer — redundant given the character-allowlist already blocks every identifier outside `{sqrt, sin, cos, log, abs}`; not adding two overlapping defense mechanisms.
- `NewCommandHandler` returning `(Command, error)` so a registration failure fails plugin activation loudly — left as the pre-existing `hello`-era convention (log-and-continue) to avoid an unrelated refactor; noted as a pre-existing gap, not introduced or fixed by this feature.
- Natural log for `log()` — rejected in favor of base-10 per the calculator-convention precedent above.
- Keeping `%` as modulo in binary-infix position and percent only when strictly trailing — rejected in favor of one uniform rule (simpler, matches the task brief's recommendation, composes with implicit-multiplication without special-casing).
**Source:** `swarm-report/math-slash-command-plan-2026-08-25.md` (architect + skeptic + researcher + reviewer consilium), `swarm-report/math-slash-command-implementation-2026-08-25.md` (verified independently by the orchestrator: re-ran build/vet/test, read every changed file, deployed to a live local Mattermost instance and confirmed 6 real `/math` invocations behave as specified).
**Closes:** none new (OQ-001, OQ-002 already resolved prior to this feature — this decision records the implementation that carries them out).

## D-004 — `/math` success reply superseded to a dedicated bot post (supersedes part of D-003)

**Date:** 2026-08-25
**Status:** accepted
**Decision:** `/math` success responses no longer use `model.CommandResponseTypeInChannel` text on the raw `CommandResponse` (D-003's original choice). A dedicated bot account (`Username: "math-bot"`, `DisplayName: "Math Bot"`, `Description: "Posts results for the /math slash command."`) is registered idempotently via `p.client.Bot.EnsureBot` in `server/plugin.go`'s `OnActivate`; bot creation failure fails plugin activation (matches this function's existing precedent of failing hard on the `cluster.Schedule` error). The bot's avatar is set separately and non-fatally from `assets/math-bot-icon.png` (128x128 PNG, purple gradient rounded square, white pi symbol — now committed, was previously untracked) via `client.System.GetBundlePath()` + `os.ReadFile` + `client.User.SetProfileImage`; avatar-set failure is logged as a warning and does not fail activation. `executeMathCommand`'s success path (`server/command/command.go`) now builds a `*model.Post{UserId: <bot id>, ChannelId: args.ChannelId, RootId: args.RootId, Message: "`<expr>` = `<result>`"}` and posts it via `client.Post.CreatePost` instead of returning `CommandResponse.Text`; on `CreatePost` failure it falls back to an ephemeral error (`"Could not post the result."`) rather than posting silently nothing; on success it returns a non-nil, all-zero `&model.CommandResponse{}` (returning `nil` would make the Mattermost server fall through to a 404/"not found" path per `channels/app/command.go`). The evaluation-error path is completely unchanged — still ephemeral `CommandResponse` via `mathErrorMessage`, no bot involvement. `plugin.json`'s `min_server_version` was bumped `"6.2.1"` → `"7.1.0"` (`EnsureBotUser`'s vendored doc comment in `server/public@v0.1.21` documents a 7.1 floor); note for future editors of this field: Mattermost's manifest validator (`github.com/blang/semver`) requires strict 3-part semver — a first attempt at `"7.1"` (2-part) passed `go build`/`vet`/`test` but failed live plugin upload with `failed to parse MinServerVersion`, only caught by the E2E deploy step, not by Go tooling. See OQ-003 (resolved) for the runtime-floor verification.

**Why now:** direct user complaint (verbatim, translated): "I don't like that the user's message gets replaced. Let's instead do this: the user sends a message (we don't alter it), and the bot (created by our plugin) replies right there with a message (example) `50% + 10` = `10.5`." D-003's original success-path design (in-channel `CommandResponse` text, no bot identity) visually read as the user's own message being hijacked/replaced by the answer, since Mattermost attributes the in-channel `CommandResponse` post to the invoking user with no distinct avatar.

**Scope notes accepted as documented trade-offs (not bugs, not open questions):**
- No DM/group-DM channel-type special-casing — the bot posts uniformly into whatever channel/DM the command was invoked in, same channel-targeting as the pre-existing behavior (only post authorship changes, not channel routing).
- Attribution: every result is now bot-authored, so it is less immediately visually obvious who invoked `/math` in a busy channel than when the post was self-authored — a direct, accepted consequence of the user's own request.
- The bot account is permanent — no cleanup on `OnDeactivate`/uninstall (deleting it would orphan historical result posts in message history).
- The user's own `/math ...` invocation text still never appears as a channel message. Confirmed via research as a universal, unfixable Mattermost platform behavior: slash commands execute as a request against the server and are never posted as the raw command text by the platform, for any plugin, ever (docs.mattermost.com/integrations-guide/slash-commands.html — "it will execute without posting a message"). This feature fixes reply attribution/avatar only, not command-text visibility — noted explicitly here so it is not mistaken for an oversight later.
- Bot username `math-bot` (not bare `math`) chosen specifically to reduce collision risk against a pre-existing human username on some future install.
- Asset provenance: `assets/math-bot-icon.png` / `.svg` were generated and approved via direct user instruction earlier in the same working session that produced this feature (not a separately-logged design-review artifact prior to this entry) — this is the first place that approval is recorded in `.assistant/`. The files are now committed as part of this feature (were untracked before).

**Alternatives rejected:**
- Reposting the user's own `/math ...` text under their own identity to "un-swallow" it — rejected as a worse hack (misattributed content); the platform behavior is unchangeable anyway (see scope note above).
- Passing `pluginapi.ProfileImagePath(...)` directly into the single `EnsureBot` call — rejected because a `SetProfileImage` failure inside that option wraps and fails the *entire* `EnsureBot` call, contradicting the requirement that avatar failure must not fail activation; split into two calls instead.
- Returning `nil` from `executeMathCommand` on success (instead of `&model.CommandResponse{}`) — rejected; verified against `server/v8`'s `channels/app/command.go` that a `nil` response makes the server fall through to a "command not found" 404 path, while a non-nil empty response correctly reaches the early-return guard and posts nothing extra.
- Adding `AddChannelMember`/channel-membership calls before `CreatePost` — rejected as unnecessary; confirmed via two independent server source-code paths (`channels/app/post.go`, `channels/api4/command.go`) that plugin-authored `CreatePost` bypasses channel-membership checks entirely (the check lives at the session/REST layer, which plugin API calls don't traverse).
**Source:** `swarm-report/math-bot-post-reply-plan-2026-08-25.md` (architect + skeptic + researcher + reviewer consilium), `swarm-report/math-bot-post-reply-implementation-2026-08-25.md` (verified independently by the orchestrator: re-ran build/vet/test, read every changed file, deployed to the live local Mattermost instance, confirmed via direct REST calls that the bot account/avatar exist correctly and that real `/math 50% + 10` / `/math 2*(3+4)` / `/math sin(90)` / `/math 1/0` invocations behave exactly as specified).
**Closes:** OQ-003.
**Supersedes:** the success-path portion of D-003 (D-003's normalization/percent/log-base/package-boundary decisions are untouched and remain in effect).

## D-005 — `/math` slash command replaced with `@math-bot` mention trigger (supersedes the trigger/transport portions of D-003 and D-004)

**Date:** 2026-08-25
**Status:** accepted
**Decision:** The `/math <expression>` slash command is removed entirely — `server/command/` (registration, dispatch, `mathErrorMessage`, tests, generated mocks) is deleted, along with its `Makefile` `mock:` target and the now-orphaned `go.uber.org/mock` dependency (dropped via `go mod tidy`). In its place, `server/hooks.go` implements `MessageHasBeenPosted(c *plugin.Context, post *model.Post)` on `*Plugin`, which fires on every post the server commits (no channel/team/membership filter — inherent to the hook, confirmed against `github.com/mattermost/mattermost/server/public@v0.1.21`'s `MessageHasBeenPosted` doc contract and the pinned server source's `RunMultiHook` call site) and reacts when `@math-bot` is mentioned.

**Mention-extraction scope (Option B, human-approved):** `@math-bot` must be the first OR last token of the (trimmed) message — case-insensitive, word-boundary aware of Mattermost's username charset (`a-z0-9._-`), so `@math-bot2` does not match. A mention anywhere else in the message (mid-sentence, e.g. `what is @math-bot 2+2`) is a **silent no-op**, not an error. This is a deliberate narrowing from the feature's original spec (which asked for mention detection anywhere in the message, start/middle/end). During `/pre-feature`, the architect and skeptic consilium members independently found, with concrete repro, that stripping a mid-message mention produces either a silently wrong answer or an unparseable expression:
- `sqrt @math-bot (4)` strips to `sqrt  (4)`, which **evaluates successfully to `2`** — a result the user never asked for, not an error, and therefore the most dangerous failure mode (wrong answer presented with no error signal).
- `2+2 @math-bot 3+3` strips to `2+2  3+3`, which fails to parse — a confusing "Could not parse expression." for what looks like two valid numbers.
Three options were escalated to the user (leading-only, leading-or-trailing, anywhere-as-specified-with-accepted-risk); the user chose leading-or-trailing (Option B), preserving both `@math-bot 2+2` and `2+2 @math-bot` from the original examples while dropping the mid-message example (`what is @math-bot 2+2`) as a silent no-op rather than accepting either failure mode above. Verified live against the local Mattermost test server: `hey @math-bot what is 2+2` produces no reply at all, `@math-bot2 2+2` produces no reply at all (username-substring boundary), while `@math-bot 50% + 10` and `sin(90) @math-bot` both reply correctly.

**Guard chain against self-reentrancy/loops** (cheapest check first, since the hook fires on every server post): (1) mention extraction — pure string ops, no API call, filters out the overwhelming majority of posts immediately; (2) `post.GetProp(model.PostPropsFromPlugin) == "true"`; (3) `p.client.Post.ShouldProcessMessage(post, pluginapi.BotID(p.botUserID))` — the official Mattermost anti-loop helper (`pluginapi` package, min server version 5.2), which skips the bot's own posts, system messages, webhook posts, and other bot accounts. `pluginapi.BotID(...)` is passed explicitly rather than relying on `ShouldProcessMessage`'s default KV-based bot-ID lookup, since that default only resolves correctly when the bot was created via `pluginapi.Client.Bot.EnsureBot` writing the `mmi_botid` KV key — which this plugin does (per D-004), but relying on the explicit option avoids the coupling.

**Reply delivery:** success and bare-mention-usage-hint both post as a threaded reply (`RootId`: `post.RootId` if the triggering post is already in a thread, else `post.Id` — using `post.Id` unconditionally was found during `/pre-feature` to cause the server to reject the post with a 400 whenever the triggering message is itself already a thread reply), authored by the bot account, format `` `<expr>` = `<result>` `` unchanged from D-004.

**Errors are now also a threaded (non-ephemeral) bot reply, not ephemeral** — a change from D-003's ephemeral `CommandResponse` behavior. Researched and confirmed: `p.API.SendEphemeralPost` is structurally callable from `MessageHasBeenPosted` (no HTTP-request-cycle dependency — `api.ctx` is plugin-scoped, not per-request), but it is a pure, unpersisted websocket broadcast with no error return and no delivery confirmation, silently dropped if the target user has no live websocket session at that instant. This caveat is not hook-specific (it applies equally to `ExecuteCommand`), but it is a real reliability downgrade from D-003's original ephemeral path, which was guaranteed via the HTTP response body of the slash-command request itself — a guarantee that no longer exists once there is no request/response cycle to attach to. A threaded, persisted, non-ephemeral error reply was chosen instead, on the reasoning that (a) the triggering message is now itself a visible channel post, so an in-channel error answer is no longer additive noise the way it would have been alongside an invisible slash command, and (b) a guaranteed-delivered error beats an error that silently vanishes for a subset of users.

**Bot account:** unchanged identity (`math-bot` / "Math Bot", same avatar, same `EnsureBot` registration in `OnActivate`, same `min_server_version: 7.1.0` floor — confirmed the new hook's own floor is 5.2, so no bump needed). Only the `Description` field text changed, from `"Posts results for the /math slash command."` to `"Posts results for @math-bot mentions."` — this propagates to already-installed servers on next activation.

**Why now:** direct, explicit user direction (verbatim, translated, this session): "the /math slash command should be replaced entirely with an @-mention trigger on the bot... The user's own message... posts to the channel completely untouched." This is a further pivot beyond D-004: D-004 fixed reply attribution (bot identity/avatar) but explicitly left the underlying platform fact unchanged — the user's `/math ...` invocation text itself could never appear as a channel message, because Mattermost slash commands are intercepted client-side and never posted (documented as an accepted, unfixable trade-off in D-004's own scope notes). This decision removes the slash command entirely so there is no invocation text to swallow in the first place — the user's message is an ordinary channel post from the moment it is sent.

**Scope notes accepted as documented trade-offs (not bugs, not open questions):**
- The hook fires for every post server-wide, including channels and DMs the bot is not a member of (`CreatePost` from the plugin API already bypassed channel-membership checks for `/math`, per D-004 — this is the same property extended to a new trigger surface, not new risk in kind, but a wider surface in practice since any channel can now trigger a reply without the bot ever being explicitly added).
- No DM-only (no-mention) interaction mode: messaging `@math-bot` directly in its own 1:1 DM channel does not contain the literal mention text `@math-bot`, so it does not trigger. Out of scope for this feature.
- Message edits do not re-trigger evaluation (`MessageHasBeenPosted` fires on creation only; `MessageWillBeUpdated`/`MessageHasBeenUpdated` would be required for edit re-triggering, not implemented).
- No admin-facing opt-out/scoping toggle for the mention hook (`plugin.json`'s `settings_schema.settings` remains `[]`).
- `CLAUDE.md`'s intro line still describes the old `/math <expression>` syntax. This could not be corrected as part of this feature: the harness's `self-config-guard` `PreToolUse` hook (`.claude/hooks/self-config-guard.sh`) blocks `Edit`/`Write` on `CLAUDE.md`/`AGENTS.md`/`.claude/*` in any project with a `.harness-lock` (by design, to prevent governing-config drift as a side effect of a feature task). Left as a known follow-up requiring a deliberate human edit or `/sync` run, not a silent oversight. `AGENTS.md` was confirmed (via the reviewer consilium pass) to contain no `/math` reference at all, so nothing was needed there.

**Alternatives rejected:**
- Mention detection anywhere in the message (the feature's original spec) — rejected per the escalated decision above; see the mention-extraction-scope discussion.
- Leading-token-only (Option A, the consilium's own initial recommendation) — rejected by the user in favor of Option B, to preserve the trailing-mention example (`2+2 @math-bot`) from the original spec.
- Silence on a well-formed-but-unparseable expression after a mention (architect's suggestion, to avoid the bot "arguing" with incidental mentions) — not adopted; kept the original spec's behavior of replying with a clear error whenever the mention position matches and the remainder is non-empty, since restricting to leading-or-trailing already eliminates the vast majority of incidental-mention false positives that motivated the suggestion.
- Keeping the error path ephemeral via `SendEphemeralPost` despite its unpersisted/best-effort delivery — rejected in favor of a threaded non-ephemeral reply, per the reliability discussion above.
**Source:** `swarm-report/mention-trigger-replaces-slash-command-plan-2026-08-25.md` (architect + skeptic + researcher + reviewer consilium; architect required one retry after a mid-run API error truncated its first attempt), `swarm-report/mention-trigger-replaces-slash-command-implementation-2026-08-25.md` (verified independently by the orchestrator: read every changed file's diff directly rather than trusting exec-agent self-reports, re-ran `gofmt`/`go build`/`go vet`/`go test` independently after both implementation layers, deployed to the live local Mattermost test server, and confirmed via direct REST API calls — posting real messages as a human test user and inspecting the resulting channel post list — that all 6 scripted scenarios, including the two negative/no-op cases, behave exactly as specified).
**Closes:** none new (see OQ-003 addendum below — confirms, does not reopen).
**Supersedes:** the trigger/transport portions of D-003 (`/math` slash-command registration/dispatch in `server/command/`) and D-004 (`CommandArgs`-based `RootId`/`ChannelId` sourcing, ephemeral evaluation-error delivery via `CommandResponse`). D-002/D-003's evaluation engine, normalization pipeline, percent semantics, degrees convention, and log-base decision are unchanged and remain in effect, unconditionally reused by `server/hooks.go` via `server/mathexpr`. D-004's bot-account identity, avatar, and success-message format (`` `<expr>` = `<result>` ``) are also unchanged.
